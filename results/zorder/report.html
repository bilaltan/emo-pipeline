Which half of the optimization did the work

OPTIMIZE compacts files; ZORDER compacts and clusters. Comparing only baseline against Z-ordered cannot tell the two apart, so a compaction-only control was added in the middle. It shows the entire loading-time gain is compaction.

B and C read the same bytes to within 120 bytes out of 384 MB and produce the same single file. Z-ordering contributed nothing to loading time; the gain is fewer files, so fewer Spark tasks and less per-file overhead.

The residual 5–10% by which C beats B sits inside a known confound: conditions always ran in the order A, B, C, so later ones met a warmer JVM and page cache. Randomizing the order is on the list.

Where Z-ordering actively hurt

Z-ordering exists to skip data on a predicate, so each table was also read with a filter on its ordered column. Bytes read is the metric to trust here — it comes from Spark's own input metrics and a warm page cache cannot flatter it.

Optimization made selective reads 3.7×, 3.8× and 3.8× more expensive on three of the four tables. The Delta log says why. Phase 0 writes nodes in id order, chunk by chunk, so the baseline arxiv node table is 44 files with perfectly disjoint id ranges:

id[0..3905]   id[3906..7811]   id[7812..11717]   ...   id[166697..169342]

0 of 44 files overlap the previous file's range

That is already an ideal layout for an id predicate, obtained for free during ingestion. Compaction merges it into one file spanning every id, file-level skipping becomes impossible, and only row-group statistics inside the file remain.

Delta skips data at file granularity. Every table here compacts to a single file — which is also why B and C come out identical. With one file there is nothing to skip, and Z-ordering cannot express itself at all.

Isolating Z-ordering itself

To compare B and C at comparable file counts, the arxiv edge table was re-run with OPTIMIZE output capped at 1 MB per file.

active files2212
bytes read, src < 10001,501,8981,501,4393,164,031

Z-ordering doubled the bytes read. Of the 12 Z-ordered files, five have min(src) = 0: Z-order interleaves the bits of src and dst, so any src range is smeared across the whole dst axis and a single-column predicate cannot skip it. A plain sort on src would. (B does nothing at this cap, because compaction only merges files already below the target size.)

What this means for LakeGRL

  1. On the loading path the submitted pipeline actually uses, Z-ordering cannot help. Phase 2 reads the edge table with a full scan and a join (phases/phase2_subgraph.py:115-116); there is no predicate on src or dst for skipping to act on.
  2. Compaction is the part that pays, and it pays through file count, not bytes. The 1002-file mag edge table is the clearest case.
  3. ZORDER BY (src, dst) is the wrong shape for single-column predicates. Multi-column Z-order trades per-column selectivity for balance across columns, and the pipeline filters one column at a time.
  4. Ingestion already produces a good layout, and optimization currently destroys it for selective reads. Storage-layer work has to beat that free baseline, not just an unoptimized strawman.

Limits of this measurement

  • Local NVMe, no object store — the largest caveat. Locally, opening 1002 files costs little beyond task scheduling. On S3 each file is a separate GET with tens of milliseconds of latency, so 1002→1 should matter far more there than the 27% measured here. That is a prediction, not a measurement, and it is the first thing to check when cluster access returns.
  • Warm page cache — timings partly measure RAM. Bytes read does not, which is why it carries the argument above.
  • Fixed condition order confounds differences below about 10%.
  • Small tables — the largest is 381 MB, and all of them compact to one file, exactly the regime where Z-ordering has no room to work.
  • VACUUM was not run; the on-disk figures deliberately show the pre-VACUUM state.

Next steps

  • Re-run on ogbn-products and reddit, whose edge tables stay multi-file after compaction — the only regime where Z-ordering can be judged fairly.
  • Compare ZORDER BY (src) alone against ZORDER BY (src, dst) to test finding 3 directly.
  • Randomize condition order and add cold-cache runs.
  • Decide whether Phase 2 should push a predicate down at all. Today the pipeline cannot benefit from any layout optimization on the edge table, because it never asks for a subset of it.

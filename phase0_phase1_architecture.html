Part 1: Phase 0 — Data Loading & Transactional Ingestion

Streaming raw graph topologies into transactional Delta Lake tables on Amazon S3

Phase 0 transforms raw, unstructured graph data (from SNAP, OGB, and PyG) into five ACID-compliant Delta Lake tables on S3. Materializing the graph as columnar Delta tables enables phase-level checkpoint reuse, ACID transaction logs, partition pruning, and prevents driver/worker memory exhaustion.

Delta Table Schema Definition Role & Downstream Usage
original_nodes id (Long), label (Int), features (Array[Float]) Raw node records and feature arrays streamed directly from source archives.
nodes id (Long), label (Int), features (Array[Float]) Distributed copy optimized for relational joins and partition-level slicing.
original_edges src (Long), dst (Long) Raw directed edge list as provided by the original dataset repository.
edges src (Long), dst (Long) Undirected, deduplicated, self-loop-free canonical graph used in training.
masks id (Long), split (String) Global train, validation, and test split assignments ('train', 'valid', 'test').
Dynamic Volume Discovery Disk Safety

Dynamically scans all candidate EBS mount points (e.g. /mnt/tmp, /mnt/spark) to redirect large dataset archives and scratch files away from the 15GB root volume, eliminating AWS EMR Driver disk crashes.

  • Prevents root partition out-of-space crashes
  • Automatically prioritizes volumes with highest free capacity
Memory-Mapped Ingestion Zero-Heap

Employs memory-mapped reading (mmap) on multi-gigabyte feature arrays (e.g. 111M-node papers100M). Operating system virtual memory pages data on demand without filling the JVM or Python heap.

  • Zero Java garbage collection pauses
  • Enables processing billion-edge graphs on modest driver memory
Chunked Micro-Batching Streaming

Streams nodes in batches of 200,000 rows and edges in batches of 2,500,000 rows directly into S3 Delta tables via Spark appends, keeping executor RAM completely bounded.

  • Fixed memory footprint regardless of total dataset size
  • Direct transactional append to S3 storage
🔄 Zero-Driver-RAM Graph Symmetrization & Deduplication

To construct the canonical undirected graph without collecting billions of edges to driver RAM, Phase 0 performs a distributed self-union and deduplication directly inside Spark across YARN worker executors:

1

Reverse Directed Edges in Parallel

Generates an inverted view of the original_edges table (swapping destination to source and source to destination) as a purely distributed Spark SQL projection.

2

Union, Filter Self-Loops & Deduplicate

Performs a distributed union of original and reversed edges, eliminates trivial self-loops (src == dst), and executes a distributed hash-based deduplication across YARN workers.

3

Transactional Materialization

Writes the final canonical edges table directly to Amazon S3 in columnar Delta format, ready for community partitioning in Phase 1.

1. Distributed Label Propagation on Spark Workers

LPA runs in parallel across all cluster nodes. In each iteration, nodes broadcast their current community label across connected edges, and each node adopts the majority label proposed by its neighbors.

1

Vertex State Initialization

Each vertex is initialized with its own node ID as its community label (community_id = id) and repartitioned across executor partitions (112 or 336 partitions depending on graph scale).

2

Label Propagation via Inner Join

Executes an inner join between the canonical edges table and vertex states, mapping the source node's current community label across each edge to the destination node.

3

Frequency Aggregation & Mode Selection

Groups proposed labels by vertex ID, tallies neighborhood label frequencies, and selects the majority community label via maximum frequency reduction.

4

Lineage Truncation via Local Checkpoints

Invokes localCheckpoint() every 2 iterations to truncate Spark's Catalyst optimizer execution graph, preventing long RDD lineage trees and eliminating JVM StackOverflow errors.

2. Driver-Side Louvain & Fast ID Remapping

While distributed LPA scales to massive graphs, it can suffer from label oscillation and over-fragmentation. Louvain modularity optimization on driver memory is EMO's default algorithm for creating high-modularity, balanced subgraphs.

🧠 How the Entire Graph is Collected & Processed on the Driver

Collecting a full graph into driver memory requires careful optimization to avoid memory blowups and slow Python loops:

1

Half-Edge Filter (src < dst)

Because the graph is undirected, every undirected edge $(u, v)$ is stored as two directed rows in Delta Lake. Phase 1 applies a src < dst filter before collecting to Pandas, transferring exactly 50% fewer edge records across the network into driver RAM.

2

Vectorized Binary Search ID Remapping ($O(E \log V)$)

C-accelerated graph engines (like igraph) require contiguous 0-indexed integer vertex IDs ([0, 1, ..., V-1]). EMO eliminates slow Python hash-map loops by using NumPy's vectorized C-level binary search (np.searchsorted) to remap millions of sparse 64-bit IDs in milliseconds.

3

C-Accelerated Louvain Modularity Execution

Instantiates an igraph C-data structure and optimizes modularity with resolution parameter $\gamma = 1.0$, grouping nodes into dense subgraphs that maximize internal edge density over boundary edges.

4

Global ID Re-Mapping & Delta Persistence

Maps partition assignments back to original global 64-bit node IDs, parallelizes the result as a Spark DataFrame, and saves it transactionally to communities/louvain/ in Delta Lake on S3.
